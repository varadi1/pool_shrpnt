# Story 1.2: Microsoft 365 Integration and Teams/SharePoint Provisioning

## Status
Ready for Review

## Story
**As a** PM/Admin,
**I want** to provision Teams groups, channels, and SharePoint document libraries with folder structures,
**so that** I can automatically create the complete collaboration environment for new orders (EM)

Please read /Users/varadiimre/0SWDEV/pool_shrpnt/docs/Képernyőfotó 2025-08-08 - 11.21.34.png for reference.

## Acceptance Criteria
1. Azure AD app registrations are configured with required Graph API permissions
2. Backend can authenticate to Microsoft Graph using client credentials flow
3. Teams group and channel creation is functional and idempotent
4. SharePoint document library creation and attachment to Teams is working
5. Folder tree creation from templates is implemented with proper naming conventions
6. Rate limiting and retry logic handles Graph API 429 responses correctly
7. All provisioning operations emit audit events and use idempotency keys
8. Integration tests verify Graph API interactions with sandbox tenant

## Dev Notes

### Previous Story Insights
Story 1.1 established the foundational infrastructure including:
- Monorepo structure with api/, worker/ directories
- Core data models (contract, order_em, folder_template)
- Celery task infrastructure with provisioning queue
- Idempotency mechanism with (emId, op, scope, tsWindow) keys
- Base provisioning task structure in worker/tasks/provisioning.py
EM = [Eseti Megrendelő], CEG = [cég, partner]
Build upon this foundation by integrating Microsoft 365 services.

### Data Models
No new database tables required in this story. Use existing models from story 1.1:
- `order_em` - for EM records being provisioned
- `folder_template` - for folder structure templates (reference to folder structure template: /Users/varadiimre/0SWDEV/pool_shrpnt/docs/NEU_Folder_Structure.md)
- `audit_log` - for tracking provisioning operations
[Source: architecture/7-data-model-postgresql-15.md]

### API Specifications
While this story focuses on backend services, these will support the following API endpoints [Source: architecture/8-api-surface-examples.md]:
- `POST /api/orders/{id}/provision` - Trigger provisioning for an order
These endpoints will be fully implemented in a later story.

### Component Specifications
No frontend components in this story - backend services only.

### File Locations
Based on layered architecture [Source: architecture/6-backend-architecture-fastapi.md]:
- Graph authentication: `api/services/auth/graph_auth.py`
- Teams service: `api/services/teams/teams_service.py`
- SharePoint service: `api/services/sharepoint/sharepoint_service.py`
- Integration clients: `api/integrations/graph/` directory
- Updated provisioning task: `worker/tasks/provisioning.py`
- Integration tests: `api/tests/integration/test_graph_services.py`

### Testing Requirements
[Source: architecture/coding-standards.md#13]:
- Contract tests for Graph/SharePoint APIs using sandbox tenant
- Integration tests for provisioning workflow
- Simulate throttling/rate-limit scenarios
- Test idempotent re-execution of failed provisioning
- Mock Graph API only for unit tests, use real API for integration tests
- Coverage target: ≥80% for services, ≥90% for critical provisioning logic

### Technical Constraints
[Source: architecture/tech_stack.md#6 and architecture/4-identity-access-azure-ad-msal.md]:
- Use MSAL Python for Azure AD authentication
- Client credentials flow for app-only access
- Required Graph permissions (minimum viable set):
  - Group.ReadWrite.All
  - Sites.ReadWrite.All  
  - Files.ReadWrite.All
  - Team.ReadBasic.All
  - Directory.Read.All
- httpx client with timeout and retry/backoff adapter
- Token caching with proactive refresh

[Source: architecture/coding-standards.md#8]:
- Create-or-get pattern for all Teams/SharePoint resources
- Idempotent operations checking by name/ID before creation
- Exponential backoff with jitter for rate limiting
- Respect 429/503 responses and Retry-After headers
- Apply PRD naming conventions (year, part A/B/C, partner abbreviation)

### Testing

#### Testing Standards from Architecture
[Source: prd/20-tesztelsi-stratgia.md and architecture/coding-standards.md#13]:
- Test file location: `api/tests/integration/` for Graph API tests
- Test framework: pytest with pytest-asyncio
- Contract tests against real Graph/SharePoint endpoints in sandbox
- Rate limit simulation to verify backoff behavior
- Test patterns:
  - Idempotency verification (run same provisioning twice)
  - Error recovery and compensation
  - Permission inheritance breaking on sensitive folders
  - Naming convention validation
- Use sandbox tenant with dedicated test site
- Never test against production tenant
