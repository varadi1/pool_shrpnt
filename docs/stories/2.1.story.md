### Data Models
New tables required [Source: architecture/7-data-model-postgresql-15.md]:
- `role` - Role definitions
- `group` - Azure AD group mappings
- `membership` - User-group relationships
- `permission_assignment` - Desired permissions state
- `permission_rule` - Matrix rules
- `permission_exception` - Special case overrides

Schema design:
```sql
CREATE TABLE role (
  id UUID PRIMARY KEY,
  name VARCHAR(50) UNIQUE NOT NULL, -- NEU_Admin, NEU_PM, etc.
  description TEXT,
  priority INTEGER -- for conflict resolution
);

CREATE TABLE permission_rule (
  id UUID PRIMARY KEY,
  role_id UUID REFERENCES role(id),
  folder_type VARCHAR(50), -- standard, financial, neu_only
  permission_level VARCHAR(20), -- read, write, delete, manage
  applies_to_pattern TEXT -- folder name pattern
);

CREATE TABLE permission_exception (
  id UUID PRIMARY KEY,
  folder_path TEXT,
  role_id UUID REFERENCES role(id),
  permission_override VARCHAR(20),
  reason TEXT,
  expires_at TIMESTAMP WITH TIME ZONE
);
```

### Technical Constraints
[Source: prd/8-rbac-jogosultsg-sszefoglal.md and architecture/4-identity-access-azure-ad-msal.md]:
- Azure AD groups map to application roles
- Backend enforces permissions (frontend only hides/shows)
- Permissions are folder-level, not file-level
- Special folders have hardcoded restrictions:
  - Pénzügyi: Only financial roles
  - NEÜ-only: Only NEU roles
  - VEGLEGES: Always read-only
  - CEG_XX: Partner-specific isolation

Permission levels:
- **read**: View folder and contents
- **write**: Add/modify files
- **delete**: Remove files
- **manage**: Change permissions

Inheritance rules:
- Default: Permissions inherit from parent
- Sensitive folders: Break inheritance explicitly
- Overrides: Explicit rules trump inherited
