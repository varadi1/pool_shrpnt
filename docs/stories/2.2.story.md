# Story 2.2: SharePoint Permission Application and Manual Locking

## Status
go

## Story
**As a** PM/Admin,
**I want** to apply calculated permissions to SharePoint and manually lock folders,
**so that** the actual SharePoint permissions match our RBAC rules and I can override access when needed

## Acceptance Criteria
1. Permission application service successfully sets SharePoint permissions via Graph API
2. Bulk permission updates are processed efficiently with batching
3. Manual folder locking by PM is implemented with UI endpoint support
4. Lock states are persisted and override calculated permissions
5. Permission changes are applied idempotently with proper error handling
6. Reconciliation report shows differences between desired and actual permissions
7. All permission applications and locks are fully audited
8. Integration tests verify SharePoint permission changes

### Data Models
New/extended tables [Source: architecture/7-data-model-postgresql-15.md]:
- `lock_state` - Manual lock tracking
- `permission_assignment` - Extended for SharePoint sync status
- `reconciliation_report` - Drift tracking

Schema additions:
```sql
CREATE TABLE lock_state (
  id UUID PRIMARY KEY,
  folder_id UUID NOT NULL,
  folder_path TEXT NOT NULL,
  locked_by UUID REFERENCES users(id),
  locked_at TIMESTAMP WITH TIME ZONE,
  lock_reason TEXT,
  expires_at TIMESTAMP WITH TIME ZONE,
  lock_type VARCHAR(20), -- manual, automatic
  is_active BOOLEAN DEFAULT true
);

ALTER TABLE permission_assignment ADD COLUMN sharepoint_sync_status VARCHAR(20);
ALTER TABLE permission_assignment ADD COLUMN last_sync_at TIMESTAMP WITH TIME ZONE;
ALTER TABLE permission_assignment ADD COLUMN sync_error TEXT;
```

### API Specifications
Implement these endpoints [Source: architecture/8-api-surface-examples.md]:
- `POST /api/locks/manual` - Create manual lock
- `DELETE /api/locks/{id}` - Remove lock
- `POST /api/permissions/apply` - Apply permissions to SharePoint
- `GET /api/permissions/reconciliation` - Get drift report

Error handling:
- 429 from Graph API triggers backoff
- 4xx for invalid lock requests
- 5xx with correlation ID for sync failures

### Technical Constraints
[Source: architecture/10-microsoft-365-integrations-graph-sharepoint.md]:
- Use Graph API for all SharePoint operations
- Break inheritance only at designated sensitive folders
- Apply permissions at folder level, not file level
- Respect Graph API rate limits with backoff
- Batch operations where possible for efficiency

[Source: architecture/coding-standards.md#8]:
- Idempotent permission operations
- Check current state before applying changes
- Use create-or-update pattern
- Handle 429 responses gracefully
- Log all Graph API interactions

Lock behavior:
- Manual locks override calculated permissions
- Locks can have expiration times
- Lock reasons are required for audit
- PM role required for manual locking
- Locks survive permission recalculation
